# 开发历程：怎么做的、AI 做了什么、哪些判断是人做的

这篇不重复 `design.md` 的算法说明，也不重复 `roadmap.md` 的取舍清单。它只回答三个问题：这个项目是怎么一步步长起来的；哪些环节由 AI 生成、哪些环节由人决定；以及每类错误分别被哪道闸门拦住，拦住的证据是什么。

## 规模与时间线

31 个版本（0.2.0 → 0.7.17），26 个 `.mbt` 文件，库本体约 4300 行，全仓约 5400 行。分三段：

- **0.2 – 0.5：把核心做对。** CDCL 主循环、双监听传播、1-UIP 分析与回跳、VSIDS、相位保存、Luby 重启、学习子句归约，然后是 DRAT 证明输出与 RUP 校验、WCNF 解析、核心引导加权 MaxSAT。这一段的工作量集中在「让结果能被别人验证」：先有求解，再有证明，再有一个不依赖求解器内部状态的校验器。
- **0.6 – 0.7.5：把闭环补上。** 最优性证明导出、读入别的求解器产出的证明、加权 MaxSAT 的轮数预算、`@path` 读盘。这一段解决的是「别人能不能接手」：证明能不能交给外部工具、别人的证明能不能被我们检查。
- **0.7.6 – 0.7.17：把工程护栏补上。** 越界输入不 abort、子句池回收、1400 实例结论对拍、400 实例暴力对拍、`tools/` 五件套（audit / doccheck / doccheck_selftest / difftest / crosscheck）、pre-commit 钩子，以及 `examples/sudoku/` 这个真实场景。这一段解决的是「凭什么相信数字」：每一条写进文档的性能或正确性结论，都要有一条命令能重跑出来。

## 决定方式：先探针，再决定

这个项目里「不做」的项比「做」的多，而且大多数不是判断出来的，是量出来的。三个例子：

| 曾经的计划 | 先做的事 | 量出的结果 | 结论 |
| --- | --- | --- | --- |
| 归并排序替换插入排序（归约时按活跃度排序） | 在同机统计「需要排序的候选有多少」 | 候选最大约 5 万，替换后端到端不到 1% | 不进主线 |
| 裁剪式复算（只重放核心相关的证明行） | 用临时探针统计核心闭包占比 | k=8 35%、k=9 93%、k=10 87%，端到端只多省 6% | 不做 |
| at-least 基数网络（放宽 `weight_cap`） | 推导 k 的上界，再跑三组实例 | 上界是 `min(w_i)/wmin`，商恒为 1 | 不做，写清推导 |

共同点：**先做一次小到不进入仓库的测量，用数字否掉方向**。这也解释了为什么 `docs/roadmap.md` 里「不做」的每一条都挂着一个数据出处——评审不需要相信作者的判断，只需要重跑那条命令。

## AI 介入的边界

分工是清楚的：

- **AI 承担的**：按明确规格写实现代码（传播、分析、归约、编码）、生成测试用例、批量做声明与事实的对齐（例如把全仓的测试总数从 95 改到 99）、写文档初稿、写对拍与审计脚本。
- **人保留的**：方向裁决（做证明还是做性能；不加预处理）、边界定义（零依赖、不调外部求解器、四后端一致）、以及 **哪些不做**。最后这一条尤其重要：AI 默认倾向是「把功能补全」，而这个项目里补全过的东西大多被后续测量证伪（见上一节的表）。
- **不允许的**：让 AI 写「结论」。文档里出现的每个数字都必须来自一次可重跑的实测，AI 只负责搬运，不负责估算。

## AI 的错误，以及分别是谁拦住的

这是本节最实在的部分。四类错误，四种不同的闸门：

1. **申报书版本号与代码不一致**（写成 `v0.7.15`，实际已到 0.7.16）。拦住它的是 `tools/doccheck.sh`：它把 `docs/申报书.md` 标明的版本、README 索引区间右端与 `moon.mod` 的 `version` 三项交叉比对。这类错误人对不出来——4772 字节的正文里，一个数字错位不会有任何手感。
2. **测试数改了、文档没跟上**（代码里 95 → 99，文档还写 95）。还是 doccheck，但它当时的规则只认「共 N 个测试」这种带前缀的写法，漏掉了申报书里不带「共」的表述。于是做两件事：全仓批量对齐，同时**把规则扩宽成「两位数以上 + 个测试」**，并补进 `doccheck_selftest.sh` 的第三个用例——规则本身也要有测试，否则它只是「这次碰巧管用」。
3. **MoonBit 语法按别的语言的习惯写**（`if not s.solve([])`、子包引用库符号漏 `@lib.` 前缀、对数组元素赋值误加 `let mut`）。拦住它的不是人，是 `moon check --deny-warn`：`not` 触发 0020/4014/3002，漏前缀报 `verify_proof is unbound`，多余的 `mut` 报 `unused_mut`。这条闸门把「编译能过」和「写法符合本项目口径」合并成了一道。
4. **题面长度数错**（`"1....7.9"` 实际是 8 个字符，测试却按 9 个字符的题面断言）。拦住它的是单元测试断言本身，而不是运行时异常——因为解析层对短输入是「明确拒绝」而不是「猜」，所以错误表现为断言失败，一眼能看到是哪一行期望不成立。

四种闸门分别覆盖：**文档一致性**（doccheck）、**规则自身的有效性**（selftest）、**语言与写法**（`--deny-warn`）、**行为正确性**（测试）。这不是设计出来的分工，是逐个踩坑之后补上去的。

## 验证闭环

从提交到可发布，依次经过六层，每层都能独立重跑：

1. `moon check --deny-warn` —— 编译与告警即错误。
2. `moon test` 在 native / js / wasm / wasm-gc 四个后端各跑一遍（当前各 100 个测试）。四后端一致是有意的约束：它挡掉「只在 native 成立」的实现，比如依赖未定义行为或依赖平台整型宽度。
3. `examples/` 与 `examples/sudoku/` —— 在真实输入上端到端跑「求解 → 证明 → 校验」，并且结果由一个不看求解器内部状态的复核函数（数独里是逐行逐列逐宫检查）确认。
4. `tools/crosscheck.sh` / `tools/difftest.sh` —— 1400 个实例上，把本库的 SAT/UNSAT 结论与 CaDiCaL 对拍，UNSAT 一侧再用 `drat-trim` 独立校验证明。这一层挡的是「两个实现一起错」之外的系统性偏差。
5. `tools/maxsat_bruteforce.py` —— 400 个小实例上，用 Python 穷举所有赋值，与本库报告的最优值逐个比对。这一层挡的是加权逻辑里的记账错误。
6. `tools/audit.sh` + `tools/doccheck.sh` + `doccheck_selftest.sh` + pre-commit —— 把文档里每一条声明变成一条命令加预期输出，并验证「这些检查本身能抓住错误」。

第 4、5 层是「独立验证」：CaDiCaL 与 `drat-trim` 不是本项目写的，Python 穷举也不是同一个实现。它们的作用不是增加测试数量，而是**换一个来源确认同一个结论**。

## 对开源工作的借鉴与取舍

学方法，不抄代码；`docs/origin.md` 记了逐条出处。三处具体取舍值得写下来：

- **沿用 MiniSat 的做法**：Luby 重启序列的调度方式、相位保存、以及「重启后不清空学习子句库」的默认策略。这些是公开材料里的成熟选择，照做没有额外风险。
- **按 MoonBit 重写而非移植**：变量用整数编码而不是对象、子句用「长度 + 紧凑数组」而不是指针链表、监听表用数组桶而不是 `vector<vector>`。原因不是 MoonBit 做不到指针结构，而是这样写之后**证明输出与内存峰值都能被稳定复现**——移植式的写法在两个后端之间会出现不同的分配模式，四后端一致就守不住。
- **明确不学 CaDiCaL 的 inprocessing**：预处理会改变默认搜索路径，让仓库里几十处实测数字全部失效；更麻烦的是证明会变成「对化简后公式」的证明，外部工具拿原始公式就复核不了。这与本项目「证明必须可外部复核」的前提冲突，所以即便它是现代求解器的主流做法，这里也不做。

## 仍然空着的

- **没有下游采用。** Mooncakes 上的 `dependents` 是空的。这个数字不会因为文档写得好而变，只能等真有项目用起来。
- **没有系统性性能对比。** `docs/crosscheck.md` 比的是**结论**，不是耗时；本仓库不主张性能优势，也不给跨机器的计时排名。`docs/benchmarks.md` 里的数字只在同一台机器、同一份证明、同一组参数下可比。
- **没有预处理、没有并行、没有百万变量级实测。** 三条都在 `docs/roadmap.md` 末尾标着 `[ ]`，理由也写在那里。

写这些不是自谦。初审要判断的是「这个东西真的在工作吗、边界清楚吗」，而边界写得越具体，越容易被验证。
